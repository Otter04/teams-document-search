# 비전 LLM을 포함하는 공통 블록 설계

작성일: 2026-10-15 · 규격 버전: 1.0.0 · 상태: 구현에 사용할 설계안

**문서 보강 후속:** 비전 테스트를 보류한 상태에서 [규칙 기반 메타데이터 추출·평가](../enrichment-run-001/README.md)를 진행했습니다. 원문 블록은 유지하고 별도 보강 JSON에 값·근거·처리 상태를 저장합니다.

**후속 구현(2026-10-16):** [네이티브 파서와 원문 평가 연결을 구현하고 110문서를 재실행](../parsing-run-003/README.md)했습니다. 아래 예시는 10월 15일의 설계 자료로 유지합니다. 비전 LLM은 아직 실행하지 않았으며 다음 시험 서비스는 OpenRouter입니다.

**공통 블록은 서로 다른 파일의 내용을 같은 방식으로 저장하는 중간 형식입니다.** Word의 문단, Excel의 표, PDF 속 구성도는 각각의 구조를 유지하면서 원문 위치와 추출 근거를 함께 가집니다. 비전 LLM의 설명도 이 형식에 담습니다. 이 블록을 다음 단계에서 보강하고 검색용 청크로 나눕니다. 블록 자체가 300~500토큰의 청크라는 뜻은 아닙니다.

이 폴더의 결과물은 규격·평가 기준·실제 자료 기반 예시입니다. 네이티브 파서의 새 형식 전환은 후속 구현에서 완료했으며 **비전 LLM 선정·연동·실행과 의미 평가기 구현은 아직 남아 있습니다.** 예시는 `record_kind: design_example`, `method: manual_design`으로 표시했습니다. 원본 자료와 대조해 작성한 예시를 모델 출력이나 평가 성적으로 취급하지 않습니다. OCR 엔진과 기준선에 대한 설계는 포함하지 않습니다.

## 공통 블록의 기본 구성

| 구성 | 담는 내용 | 이유 |
|---|---|---|
| 식별자·종류 | `block_id`, `type`, `parent_id`, `order` | 문단·표·그림을 구분하고 부모 관계와 읽는 순서를 보존 |
| 원문 | `text` | 파일이나 이미지에서 읽은 글자만 보존 |
| 구조 | `table`, `cells`, `visual.nodes`, `visual.relations` | 셀의 행·열, 병합, 그림의 대상과 연결 관계를 보존 |
| 해석 | `claims` | 그림이 전달하는 내용을 짧은 주장 단위로 설명하고 관찰·추론을 구분 |
| 근거·위치 | `loc`, `evidence` | 페이지·영역·셀·줄을 통해 원본을 다시 확인 |
| 문맥 | `heading_path`, `context_ids` | 관련 제목·캡션·앞뒤 문단을 연결 |
| 처리 이력 | `run_ref` → `runs` | 어떤 파서/모델·프롬프트·입력 이미지에서 나왔는지 추적 |

`text`에 “이 구성도는 자동 장애 전환을 보장한다” 같은 해석을 섞지 않습니다. `claims.status=observed`는 그림·문서에서 직접 확인되는 주장, `inferred`는 그 근거로부터 추론한 주장입니다. 둘 다 근거를 연결합니다. **모델이 observed라고 표시했다고 참이라는 뜻은 아니며, 평가에서 원본과 대조해야 합니다.**

예를 들어 사진에 랙 2개가 보이면 “랙 2개가 보인다”는 관찰로 기록할 수 있습니다. 주변 제목이 “서버실 이전”이라고 해서 사진만으로 이전 완료나 정상 가동을 확정할 수는 없습니다. 제목에서 읽은 사실과 사진에서 본 사실을 따로 연결합니다. 사진 예시는 현재 데이터셋의 실제 검증 사례가 없어 별도 양식만 제공합니다.

검색용 문장은 후속 청킹 단계에서 **원문 + 근거가 있는 관찰 설명 + 구조를 풀어 쓴 설명**으로 만들고, 추론은 기본 검색 입력에서 제외하도록 제안합니다. 원문과 해석의 저장 경계를 유지해야 원문 누락과 의미 이해를 따로 평가할 수 있습니다.

## 예비 데이터셋의 실제 자료로 보면

예비 세트는 110문서(DOCX 13, PPTX 21, XLSX 23, PDF 20, TXT 8, LOG 25)입니다. 아래 파일은 원본 해시를 대조했고, 예시에 필요한 원문·셀·도형 문자와 스캔 이미지를 확인했습니다. 전체 재파싱 결과가 아닌 일부 영역의 설계 예시입니다.

### D-005: Word 계약서의 제목과 본문

`2025 MES 고도화 구축_계약서(초안).docx`의 7번째 문단은 `제2조(계약기간)`, 8번째 문단은 `본 계약의 기간은 2025년 3월 1일부터 2025년 8월 31일까지로 한다.`입니다.

두 문단을 각각 `heading`과 `paragraph`로 저장하고, 본문에서 제목을 `context_ids`로 참조합니다. Word의 실제 페이지는 렌더링 환경에 따라 달라지므로 예시는 페이지를 지어내지 않고 `paragraph_index: 8`로 위치를 기록합니다. 날짜를 정규화한 문서 메타데이터는 후속 보강 단계의 일입니다.

### D-003: Excel 견적서의 표와 병합 셀

`견적서_2025 MES 고도화 구축_v1.xlsx`의 `견적서!A12:F16`은 아래 표입니다.

| No | 품목 | 규격 | 수량 | 단가 | 금액 |
|---:|---|---|---:|---:|---:|
| 1 | 애플리케이션 구축 인건비 | M/M 기준 | 1 | 132700000 | 132700000 |
| 2 | 서버 H/W | 일식 | 1 | 66350000 | 66350000 |
| 3 | S/W 라이선스 | 일식 | 1 | 39810000 | 39810000 |
| 4 | 설치 및 기술지원 | 일식 | 1 | 26540000 | 26540000 |

하나의 `table` 아래에 5개의 `table_row`를 둡니다. 셀마다 값·행·열·원본 셀 주소를 보존합니다. **표 내부 2행은 원본 Excel의 13행**이며 이를 구분합니다. 예를 들어 금액 셀은 `row: 2`, `column: 6`, `loc.cell_range: F13`입니다.

같은 파일의 `A1:F1`은 `견 적 서`라는 병합 셀입니다. 여섯 셀에 글자를 복제하지 않고, A1에 해당하는 셀 하나에 `column_span: 6`을 기록합니다. 수식과 표시 형식도 저장할 자리는 두되, 원본에 없는 수식을 만들지 않습니다.

### D-044: 스캔 계약서도 같은 표 형식

`PACS 스토리지 증설_계약서(서명본).pdf`의 2쪽에는 다음 4행·2열 표가 있습니다.

| 갑 | 을 |
|---|---|
| 상호: 의료법인 새봄의료재단 | 상호: 라움정보기술 주식회사 |
| 대표이사: 류정원 (인) | 대표이사: 정태오 (인) |
| 주소: (생략) | 주소: 서울특별시 구로구 디지털로 000, 7층 |

이것도 `table → table_row → cells`입니다. 차이는 입력이 페이지 이미지이고, 구현 시 `run_ref`가 비전 LLM 실행을 가리킨다는 점입니다. 마지막 주소가 두 줄로 보이더라도 한 셀로 유지합니다. 파일명의 “서명본”이나 `(인)`이라는 글자만으로 실제 날인을 확인했다고 기록하지 않습니다.

예시의 좌표는 표 전체의 근사 영역입니다. 셀별 정밀 좌표를 검증한 결과는 아닙니다. 원본 확인용 [2쪽 이미지](assets/D-044-2.png)를 함께 보관했습니다.

### D-069: 구성도는 글자와 연결 관계를 함께 저장

`DDC_네트워크구성도_검토본_스캔.pdf`에는 본사·DR 네트워크가 그려져 있습니다. [원본 페이지 이미지](assets/D-069-1.png)에서 **8개 상자와 7개 연결선**을 확인해 예시를 만들었습니다.

- `text`: `코어 스위치`, `Cisco N9K-C93180YC × 2`, `본사 서버팜`, `10.65.10.0/24` 등 실제 표기.
- `visual.nodes`: 코어 스위치, 본사 서버팜, DR 서버팜, 복제망 등의 대상과 각 영역.
- `visual.relations`: 코어 스위치와 각 서버팜·복제망을 잇는 선. 방향 화살표가 없으므로 `direction: undirected`.
- `claims`: “도면에서 코어 스위치와 본사 서버팜 사이에 연결선이 있다.”라는 설명과 해당 선·상자의 근거.

구조 부분을 줄여 보면 다음과 같습니다. 전체 레코드는 [D-069 예시](examples/pdf-diagram-D-069.json)에 있습니다.

```json
{
  "from_node": "core",
  "to_node": "hq",
  "direction": "undirected",
  "label": null,
  "evidence_ids": ["edge-5"]
}
```

이 선은 연결 관계를 보여 줍니다. 본사 서버팜과 DR 서버팜의 직접 연결, 단방향 트래픽, 자동 장애 전환, 실제 정상 가동까지 보여 주지는 않습니다. 그런 주장이 생성되면 의미 평가에서 근거 부족으로 판정합니다. 여기의 노드·관계는 **해당 그림 내부 구조**이며 별도 GraphRAG 도입을 뜻하지 않습니다.

## 파일 형식별 양식

**출력 파일 형식은 모두 UTF-8 JSON입니다.** 한 문서의 전체 블록을 담은 JSON 하나를 기본으로 하며, 일괄 처리 때는 한 줄에 문서 하나인 JSONL로 묶습니다. 입력 확장자마다 달라지는 것은 블록 조합과 `loc`입니다.

| 입력 | 기본 블록 구성 | 위치 기준 | 채워 쓸 양식 | 실제 자료 예시 |
|---|---|---|---|---|
| DOCX | heading / paragraph / table / figure | 문단·표·행·셀·미디어 경로 | [DOCX](templates/docx.json) | [D-005](examples/docx-D-005.json) |
| PPTX | slide → heading / paragraph / table / figure | 슬라이드·도형 ID·영역 | [PPTX](templates/pptx.json) | [D-007](examples/pptx-D-007.json) |
| XLSX | table → table_row → cells | 시트·셀 범위 | [XLSX](templates/xlsx.json) | [D-003](examples/xlsx-D-003.json) |
| 텍스트 PDF | heading / paragraph / table / figure | 페이지·영역 | [PDF 텍스트](templates/pdf-text.json) | [D-022](examples/pdf-text-D-022.json) |
| 스캔 PDF 표 | table → table_row → cells | 페이지·표/셀 영역 | [PDF 스캔 표](templates/pdf-scan-table.json) | [D-044](examples/pdf-scan-table-D-044.json) |
| PDF 구성도 | figure + nodes / relations / claims | 페이지·대상/선 영역 | [PDF 구성도](templates/pdf-diagram.json) | [D-069](examples/pdf-diagram-D-069.json) |
| TXT | paragraph | 시작 줄·끝 줄 | [TXT](templates/txt.json) | [D-052](examples/txt-D-052.json) |
| LOG | log_line | 시작 줄·끝 줄 | [LOG](templates/log.json) | [D-010](examples/log-D-010.json) |
| 문서에 포함된 사진 | figure + claims + 문맥 참조 | 삽입 미디어·주변 문단 등 | [사진](templates/embedded-photo.json) | 실제 사진 평가는 별도 자료 보강 필요 |

양식은 입력 구조를 보여 주기 위해 일부 예시 위치와 행 수를 유지했습니다. `REPLACE` 값만 바꾸면 완성되는 것은 아닙니다. 실제 자료에 맞게 블록 수·위치·근거·처리 단위 목록·실행 정보를 채워야 합니다. 독립 사진 파일의 수집 지원 범위를 새로 추가한 것은 아닙니다.

## 평가와 다음 구현 범위

평가는 **형식·누락 → 원문 보존 → 표/구성도 구조 → 의미와 근거** 순서로 진행합니다. 파일을 읽었다고 성공으로 판정하지 않고, 필요한 모든 페이지·슬라이드·표·그림이 처리됐는지 별도 목록과 비교합니다. 모델의 설명이 원문 필수 문자열 검사를 대신 통과시키지 않게 합니다.

상세 기준과 초기 제안값은 [평가 설계](EVALUATION.md), 필드의 정확한 규칙은 [규격 설명](SCHEMA.md), 기계 검증용 양식은 [JSON Schema](common-block.schema.json)에 있습니다. 기존 문자열 평가기에 연결할 때는 원문만 내보내는 변환 계층이 필요합니다. 의미 평가는 별도 결과로 관리하며 기존 평가기의 점수라고 표시하지 않습니다.

현재 후속 범위는 **OpenRouter 모델 비교 → 비전 LLM 출력 어댑터 연결 → 독립 검수한 정답 확장 → 시각 자료 실행·평가**입니다. 원본 예비 세트와 기존 실험 결과는 변경하지 않았습니다.

## 이번에 확인한 것

- 예시 8개와 양식 9개: JSON 스키마·참조·표 셀 구조 검사 통과.
- 오류 입력 14가지: 누락 필드, 존재하지 않는 대상/근거, 순환 부모, 뒤집힌 좌표, 셀 겹침 등 거부 확인.
- 예시 원본 8개: 파일 해시 대조. 네이티브 자료 6개의 문단·셀·도형 문자·줄 76항목을 원문과 재대조했고, 스캔 예시 2개는 페이지 이미지를 확인.

검사 기록은 [형식 검증](verification.json), [원본 대조](source-inspection.json), [작업 상태](package-status.json)에 있습니다. 이 통과는 **설계 파일의 일관성 검사 결과**이며 비전 LLM의 파싱 성능 통과를 의미하지 않습니다.
