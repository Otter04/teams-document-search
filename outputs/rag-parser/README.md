# 문서 파싱 기준선

**기존 구현의 재현 안내:** 이미지 처리 설계는 비전 LLM을 사용해 의미와 구조, 문서 맥락을 추출하는 방향으로 변경했습니다. OCR 엔진 선택·오류 교정·기준선 개선은 앞으로의 설계에서 제외합니다. 아래는 이미 실행한 OCR 코드의 동작과 재현 방법이며 현재 권장 파이프라인이 아닙니다. [현재 방향과 다음 작업](../parsing-run-002/README.md#현재-설계-방향)을 참고하세요. 비전 LLM 연동은 아직 구현하지 않았습니다.

실제 파일을 읽어 텍스트와 구조·위치를 공통 JSON 블록으로 저장합니다. 이 단계의 블록은 검색용 청크와 다릅니다. 거래처나 문서종류를 분류하는 LLM 보강, 300~500토큰 청킹, 임베딩·색인·검색은 수행하지 않습니다.

## 이번 실행

`../parsing-run-001/README.md`에 실제 문서 110건의 결과와 제한을 정리했습니다. `parsed.jsonl`은 실제 파싱 결과이며 평가기를 검증하기 위한 가상 입력이 아닙니다. 데이터셋 자체는 제공된 가상 업무 문서입니다.

## 형식별 출력

| 형식 | 변환 단위 | 보존하는 위치·구조 |
|---|---|---|
| DOCX | 제목, 문단, 표의 행 | 문단 번호, 표·행·열, 병합 셀 원점, 제목 경로 |
| PPTX | 슬라이드 | 슬라이드 번호, 도형 ID·좌표, 표의 행·열, 발표자 노트 |
| XLSX | 시트의 행 | 시트·행·셀 주소, 병합 원점, 헤더 후보, 수식과 저장값 |
| 텍스트 PDF | 텍스트 줄, 제목, 선으로 구분된 표의 행 | 실제 페이지, 좌표, 표·행·열 |
| 스캔 PDF | 페이지와 내부 OCR 줄 | 실제 페이지, 정규화 좌표, OCR 신뢰도·엔진 순서 |
| TXT | 빈 줄로 구분된 문단 | 시작·끝 줄 번호, 원래 인코딩 |
| LOG | 로그 한 줄 | 줄 번호, 시각, 명시된 수준, 오류코드 후보 |

모든 블록에는 `type`, `text`, `loc`, `heading_path`, `block_id`가 있습니다. PPTX 슬라이드와 OCR 페이지의 세부 구조는 `elements`에 있습니다. 표는 원문 셀의 대응 관계를 `cells`에 유지합니다. 이후 청킹 단계는 이 구조를 참조해야 합니다.

### 적용 규칙

- DOCX는 제목 스타일·개요 수준을 우선합니다. 제공된 계약서는 제목 스타일을 사용하지 않아 독립된 `제N조(...)`와 큰 글자 제목을 보조 규칙으로 인식합니다. 사용한 규칙을 `heading_method`에 기록합니다.
- DOCX의 삽입 변경은 포함하고 삭제 변경은 제외합니다. 일반 머리글·바닥글은 본문에 넣지 않고, 계약번호가 있으면 `details.header_footer_identifiers`에 별도로 남깁니다.
- DOCX의 실제 쪽 번호는 레이아웃 계산 없이 알 수 없으므로 만들어 넣지 않습니다. 문단·표 위치를 제공합니다.
- PPTX 제목 자리표시자가 비어 있으면 가장 위쪽 텍스트를 제목 후보로 사용합니다. 도형 텍스트와 발표자 노트도 보존합니다. 도형 연결선의 의미를 추론하지 않습니다.
- XLSX 병합 영역의 각 셀은 원래 값을 공유하되 `source_cell`로 원점을 남깁니다. 펼친 검색 텍스트에는 같은 행의 병합값을 한 번만 넣습니다.
- XLSX 정식 Table 헤더가 있으면 사용하고, 없으면 문자 셀이 3개 이상인 행을 헤더 후보로 기록합니다. 제목·메모가 오인될 수 있으므로 확정 라벨이 아닙니다.
- 숨김 시트는 기본적으로 포함해 내용 손실을 피하고 상태를 기록합니다. `--hidden-sheets exclude`로 바꿀 수 있습니다. 이는 기준선 구현 선택이며 운영 정책의 최종 확정이 아닙니다. 실제 예비 세트에는 숨김 시트가 없습니다.
- XLSX 수식은 계산하지 않고 저장된 결과값을 읽습니다. 저장값이 없으면 경고를 남기고 부분 처리로 표시합니다. 예비 세트에는 수식 셀이 없어 별도 테스트 파일로 이 동작을 확인했습니다.
- PDF는 페이지별 공백 제외 텍스트가 20자 미만이면 OCR을 사용합니다. 임계값은 `--min-pdf-chars`로 설정합니다. 텍스트 레이어에 일부 글자만 있고 나머지가 이미지인 혼합 페이지는 이 기준만으로 누락을 발견하지 못할 수 있습니다.
- 텍스트 PDF의 선 기반 표를 복원합니다. 복잡한 무테두리 표와 여러 단 편집은 추가 검증이 필요합니다.
- OCR은 글자와 좌표만 저장합니다. 좌표로 위→아래, 같은 줄 안에서는 왼쪽→오른쪽 순서를 정리하고 엔진의 원래 순서도 보존합니다. **스캔 표의 행·열이나 구성도 연결 관계를 복원하지 않습니다.**
- TXT/LOG는 UTF-8을 먼저 엄격하게 읽고 실패하면 CP949를 사용합니다. UTF-16은 BOM이 있을 때만 지원합니다. 손상된 바이트를 임의의 대체 문자로 바꾸지 않습니다.

## 기존 실험 재현

Python 3.10 이상이 필요합니다. 검증 환경은 Python 3.12, macOS ARM64입니다.

```sh
python3 -m pip install -r requirements.txt
```

macOS 로컬 OCR 실행기를 빌드합니다. 개발 도구의 Swift 컴파일러가 필요합니다.

```sh
mkdir -p build
swiftc -module-cache-path build/swift-cache vision_ocr.swift -o build/vision-ocr
build/vision-ocr --languages
```

입력 manifest는 문서 ID와 상대 경로 **두 필드만** 포함합니다. 파서는 `gold/`, 필수 문자열, 정답 메타데이터, OCR 평가용 전사본을 읽지 않습니다.

```json
{"doc_id":"D-005","relative_path":"sites/영업1팀/Shared Documents/청람정밀/2025_2025 MES 고도화 구축/계약/2025 MES 고도화 구축_계약서(초안).docx"}
```

이번 실행의 실제 manifest는 `../parsing-run-001/manifest.jsonl`입니다. 다음처럼 새 출력 폴더를 지정합니다.

```sh
python3 parse.py \
  --files-root '/path/to/dataset/files' \
  --manifest '../parsing-run-001/manifest.jsonl' \
  --ocr build/vision-ocr \
  --output '/path/to/new-parsing-run'
```

PPTX 삽입 이미지 OCR은 `--ocr-images`로 켭니다. 예비 PPTX에는 삽입 그림이 없어 이번 실제 측정에서 해당 기능은 사용하지 않았습니다.

출력은 `parsed.jsonl`, 입력 manifest 사본, `provenance.json`입니다. 파일별 원본 SHA-256, 파서 버전, 라이브러리 버전, OCR 설정·실행기 해시, 처리시간, 경고를 남깁니다. 파일 읽기에 실패하면 해당 문서는 빈 블록과 실패 원인을 기록하며 전체 실행 종료 코드는 1입니다. `partial` 상태가 있으면 경고와 누락 기능을 반드시 검토하세요.

### 기존 OCR 실행기 인터페이스

`--ocr` 실행기는 이미지 경로 하나를 인수로 받고 다음 형태의 JSON을 표준 출력으로 반환해야 합니다.

```json
{"engine":"engine-name","revision":1,"languages":["ko-KR","en-US"],"lines":[{"text":"인식한 글자","confidence":0.95,"bbox":[0.1,0.1,0.6,0.15]}]}
```

좌표는 왼쪽 위 원점의 0~1 정규화 값 `[x0,y0,x1,y1]`입니다. 실패 시 종료 코드 0 이외를 반환합니다. 이 인터페이스는 기존 OCR 실험을 재현하기 위한 규격입니다. 비전 LLM을 포함한 새 출력은 [공통 블록 설계안](../common-block-design/SCHEMA.md)에 따르며 이 코드에는 아직 반영하지 않았습니다.

기존 실험은 Mac의 Apple Vision을 사용했습니다. 이 기록은 운영 OCR 엔진 선정이나 Spark용 OCR 검증을 다음 작업으로 요구하지 않습니다. 현재 후속 작업은 새 공통 블록 규격에 맞춘 비전 LLM 연결과 실제 평가입니다.

## 평가 연결

기존 평가기에 `--parsed 새결과/parsed.jsonl`을 넘깁니다. 청킹·메타데이터·검색 입력은 이번 단계에서 제공하지 않습니다.

```sh
python3 ../rag-evaluator/evaluate.py \
  --dataset '/path/to/dataset' \
  --parsed '/path/to/new-parsing-run/parsed.jsonl' \
  --run-info '/path/to/run-info.json' \
  --manual-metrics '/path/to/measured-metrics.json' \
  --output '/path/to/new-evaluation'
```

`validate.py`는 이번 110건 자료에 대한 **별도 평가 코드**입니다. 24개 표·시트 영역을 직접 OOXML 또는 페이지 전사본과 비교하고, OCR 전사본을 사용해 CER을 측정합니다. 파서가 이 전사본을 읽어 오독을 고치는 기능은 없습니다. 다른 데이터셋에는 표본 선택 ID와 전사본을 새로 준비해야 합니다.

`cache_workbook.py`는 LibreOffice에서 재계산한 사본의 값을 원래 엑셀에 캐시로 넣는 보조 도구입니다. 입력과 수식이 일치할 때만 처리하며 원래 셀 값·서식은 유지합니다. 숫자는 파일 저장 과정의 1e-14 이내 반올림 차이만 허용합니다.

## 테스트와 범위

```sh
python3 -m pip install -r requirements-test.txt
python3 -m unittest discover -s tests -v
```

11개 구조 테스트는 문단·표 순서, 제목 경로, 변경 추적, 병합 셀, 헤더의 계약번호, 숨김 시트, 수식 저장값, 도형·노트·표, CP949, 로그, PDF 표 위치, OCR 읽기 순서를 확인합니다. 실제 데이터에 없는 기능의 단위 테스트는 실제 업무 문서에서 검증했다는 의미가 아닙니다.

구형 `.doc/.ppt/.xls`, HWP/HWPX, 중첩 Word 표, 복잡한 페이지 레이아웃, 실제 SharePoint 수집·동기화는 이번 기준선의 지원 완료 범위에 포함되지 않습니다. 원본 링크·SharePoint ID·권한 정보는 실제 수집 단계가 연결될 때 별도로 추가해야 합니다.
