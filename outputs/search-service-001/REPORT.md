# 검색 첫 구현·실행 결과

2026-10-20. **110개 예비 문서를 검색하는 API와 확인 화면을 Orin에서 실행했다. 최종 개발 평가 Hit@5는 59/61, 96.72%다. 전체 품질 기준의 최종 통과는 아니다.**

[검색 화면](http://127.0.0.1:18020/) · [설계와 기술 선택](../../docs/SEARCH_DESIGN.md) · [최종 비교 원자료](evaluation/corrected-004/summary.json) · [반복 실행](evaluation/repeat-005/summary.json)

## 구현된 흐름

질문 → 규칙 분석·조건부 Qwen3.6 보조 → Elasticsearch Nori/BM25 + bge-m3 벡터 검색 → RRF → 코드 기반 R1 → 문서·버전 묶기 → 원문 발췌와 위치를 담은 카드.

- 기존 110문서, 원문 1,072청크 + 의미 보강 17청크, 벡터 1,089개를 재사용했다. 새 문서 임베딩·비전 처리·보강 생성은 하지 않았다.
- bge-m3는 기존 파일을 한 번 로딩해 질문 임베딩에 재사용한다. Qwen도 기존 Orin 서버를 사용한다. 외부 유료 API 호출과 새 모델 다운로드는 없다.
- 검색창만 제공한다. 조건은 읽기 전용으로 보여주고 최대 5문서·문서당 최대 3개 직접 발췌를 반환한다. 의미 일치만 있으면 발췌 1개다.
- 출처 블록과 문자 범위를 되짚을 수 있다. DOCX 문단, PDF 페이지, 슬라이드, 엑셀 셀, 로그 줄 위치를 표시한다. 생성형 답변은 만들지 않는다.
- 문서 종류·날짜 등 조건 A/B와 R0/R1의 개발 비교를 수행했다. **개발 확인용 기본값은 B+R1**이다. 기존 색인 별칭을 바꾸거나 최종 운영 검색으로 승격하지 않았다.

## 최종 비교

| 방식 | 정답이 상위 5문서에 보인 질문 | 비율 | MRR@5 | 정답이 검색 후보에 포함된 질문 |
|---|---:|---:|---:|---:|
| A + R0: 거래처·종류·날짜·상태 강제 | 54/61 | 88.52% | 0.775 | 60/61 |
| B + R0: 거래처만 강제 | 55/61 | 90.16% | 0.775 | 60/61 |
| **B + R1: 코드 기반 순위 조정** | **59/61** | **96.72%** | **0.818** | **60/61** |

A/B는 1문항 차이이므로 설계의 다음 기준인 ‘강제 조건 때문에 정답이 제외된 경우’를 비교했다. B는 0건이다. A는 원래 정답 중 하나 이상이 제외된 질문이 3개이며, 그중 모든 정답이 제외된 질문은 1개다. 이 3개를 모두 잘못된 필터로 단정하지 않는다. 예를 들어 Q-022의 ‘서명본’ 요청에서 초안을 제외한 것은 질문에 부합하지만, 원래 정답에는 초안도 포함돼 있다. 최종 B 선택에는 영향이 없다.

R1은 B+R0보다 4문항 개선했고 유형별 하락이 없으며 응답 시간 기준을 만족해 개발 화면에 사용한다. R1 가중치는 실행 전에 고정한 값을 유지했다. 정답 문서 ID에 따른 점수나 별도 번호 상단 고정 분기 2a는 넣지 않았다.

| 질문 유형 | B+R1 | 설계의 잠정 기준 | 결과 |
|---|---:|---:|---|
| 메타데이터형 | 19/19 | 18/19 이상 | 충족 |
| 번호형 | 15/16 | 15/16 이상 | 충족 |
| 의미형 | 20/21 | 17/21 이상 | 충족 |
| 혼합 | 5/5 | 4/5 이상 | 충족 |

여기서 Hit@5는 설계 문서의 ‘Recall@5: 정답이 하나라도 보인 질문 수’와 같은 정의다. 정답 여러 개를 모두 찾은 비율과는 다르다. 원래 정답 문서 각각의 재현율 평균은 **71.31%**다. 이번 화면은 같은 문서의 여러 버전을 한 카드로 묶으므로 이 수치를 과거 ‘버전별 문서를 별도 결과로 나열한 Recall’과 그대로 비교하면 안 된다. 접힌 다른 버전을 정답 노출로 가산하지 않고 대표 카드 기준으로 엄격하게 채점했다.

## 처리 시간과 LLM 상태

| 경로 | 표본 | 최초 최종 비교 p95 | 반복 실행 p95 |
|---|---:|---:|---:|
| 규칙만 사용 | 52질문 | 0.374초 | 0.353초 |
| LLM 보조를 시도 | 9질문 | 2.789초 | 2.860초 |

서버가 질문을 받은 뒤 결과 카드·발췌·위치·버전 정보를 완성할 때까지 측정했다. 질문 임베딩 결과 캐시는 쓰지 않았다. 모델을 상시 로딩한 상태의 순차 요청 결과이며 모델 최초 로딩 시간·Mac/VPN 왕복·브라우저 표시·동시 사용자 부하는 제외한다. 실제 SharePoint 링크가 없는 자료에서 `url:null`까지 구성한 시간이다.

**최종 두 실행에서 LLM 보조 9건은 각각 모두 2.5초 대기 제한을 넘겨 규칙으로 돌아갔다.** 빠르게 올바른 JSON을 만들어 냈다는 뜻이 아니다. 초기 3초 제한 실행에서는 1건을 채택했으나, 전체 응답 시간이 약 3.2초로 목표를 넘었다. 검색에 0.5초의 시간을 남긴 뒤에는 지연 목표를 맞췄지만 LLM 분석의 실효성은 미완이다. 모델 자체의 정확도 실패로 단정하지 않고 시간 제한과 출력 형식의 처리 비용을 다음 과제로 둔다.

## 이전 색인 평가와의 차이

이전 Elasticsearch 연결 평가의 Hit@5는 60/61, 98.36%였다. 이번은 59/61, 96.72%로 1문항 낮다. 이전 검증은 기존 필터·필드 가중치와 문서별 BM25 정렬을 재현하는 평가였다. 이번은 설계의 **청크당 각 50개 → RRF 30개 → R1 → 문서·버전 묶기**를 실제 서비스로 연결한 평가다. 단순히 같은 검색 API에 화면만 붙인 것이 아니다.

새 구조에서 메타데이터형은 18/19 → 19/19, 번호형은 16/16 → 15/16, 의미형은 21/21 → 20/21, 혼합은 5/5 유지다. 기존 원문과 벡터가 사라져 생긴 차이가 아니라 후보 제한·결합·조건 해석 변경의 효과다. 이전 색인과 결과를 보존하고, 새 구조는 개발 상태로 분리했다.
